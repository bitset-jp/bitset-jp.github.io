# i18n Architecture

## Decision

Use Astro's built-in i18n routing with a **page template component pattern** and a **centralized translation dictionary**, rather than duplicating full pages or using a third-party i18n library.

## Context

The site needs to support Japanese (default) and English. We evaluated three approaches:

1. **Duplicate pages per locale** — copy each page, translate inline. Simple but doubles maintenance burden and causes content drift.
2. **Third-party i18n library** — adds a dependency, may not integrate cleanly with Astro's static generation.
3. **Template components + translation dictionary** — shared logic, centralized strings, thin route wrappers. Chosen approach.

## How It Works

### Routing

Configured in `astro.config.mjs`:

```js
i18n: {
  locales: ['ja', 'en'],
  defaultLocale: 'ja',
  routing: { prefixDefaultLocale: false },
}
```

- Japanese pages: `src/pages/*.astro` → served at root (`/about`)
- English pages: `src/pages/en/*.astro` → served at `/en/about`

Both import the same template component:

```astro
---
import AboutTemplate from '../components/pages/AboutTemplate.astro';
---
<AboutTemplate />
```

### Translation Dictionary

`src/i18n/translations.ts` exports a `ui` object keyed by locale, then by dot-separated string ID:

```ts
ui.ja['nav.home']  // → 'ホーム'
ui.en['nav.home']  // → 'Home'
```

### Utility Functions

`src/i18n/utils.ts` provides:

- `useTranslations(lang)` — returns a `t(key)` function bound to the locale
- `getLocalizedPath(path, lang)` — converts a path to its locale-prefixed form
- `getAlternateLang(lang)` — returns the other supported locale
- `getLangFromUrl(url)` — extracts locale from a URL pathname

### Product Content

Product markdown files contain both languages in frontmatter fields:

| English field | Japanese field |
|---------------|----------------|
| `title` | `titleJa` |
| `description` | `descriptionJa` |
| `features` | `featuresJa` |
| `specs` | `specsJa` |

Templates select the correct field using `Astro.currentLocale`.

## Trade-offs

- **Pro**: Zero code duplication between locales — one template serves both
- **Pro**: All strings in one file — easy to audit for missing translations
- **Pro**: No additional dependencies
- **Con**: Translation file grows linearly with page count — manageable at current scale
- **Con**: Long-form markdown uses two channels — English in the file body, optional Japanese in frontmatter `bodyJa` (rendered via `@astrojs/markdown-remark`), which is slightly less ergonomic than two `.md` bodies side by side

## Future Considerations

- If a third language is added, the same pattern extends — add a new locale to the config, a new column to `translations.ts`, and a new `src/pages/{lang}/` directory
- If editors prefer Japanese as the primary markdown file body, swap convention (Japanese file body + optional `bodyEn` string) — would require template and content migration
